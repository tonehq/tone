⏺ Design is clear. Here's what I found:

  Data source: call_metrics.turn_metrics (JSONB array) already stores per-turn
  stt_ttfb, llm_ttfb, tts_ttfb, and end_to_end — exactly the four series you
  asked for. computed_stats is per-call and doesn't split by service, so it
  can't power this view.

  Plan (following the project's layered pattern + DRY):

  1. Add CallService.filtered_calls_query() — a single source of truth for "the
  filter scope" (same joins + _apply_filters used by /list and /facets, minus
  pagination). Both the new endpoint and any future analytics endpoints can
  consume it.
  2. New file core/services/call_metrics_analytics_service.py — pure aggregation
   logic (count / avg / p50 / p95 / p99 / min / max + fixed-bucket histogram)
  reusing _avg / _percentile from call_metrics_service.
  3. POST /call-log/metrics-summary in core router with a MetricsSummaryRequest
  schema.
  4. Same endpoint mirrored in ee/api/v1/call_logs.py, reusing the core schema.

  ┌──────┬─────────┬────────────────────────────────────────┐
  │ Call │ # turns │      End-to-end latency per turn       │
  ├──────┼─────────┼────────────────────────────────────────┤
  │ A    │ 10      │ 1s, 1s, 1s, 1s, 1s, 1s, 1s, 1s, 1s, 1s │
  ├──────┼─────────┼────────────────────────────────────────┤
  │ B    │ 2       │ 5s, 5s                                 │
  ├──────┼─────────┼────────────────────────────────────────┤
  │ C    │ 2       │ 5s, 5s                                 │
  └──────┴─────────┴────────────────────────────────────────┘

  Current behavior (turn-weighted)
  - Total samples: 14 turns
  - Average: (10×1 + 2×5 + 2×5) / 14 = 2.14 s
  - Call A dominates because it has 10 turns, so the average looks fast.

  If we switched to call-weighted
  - Per-call average first: A=1s, B=5s, C=5s
  - Then average those: (1 + 5 + 5) / 3 = 3.67 s
  - Each call weighs equally, so B and C's slowness shows up honestly.

  Which one is "right"?

  Depends on what you want the number to mean:

  - Turn-weighted ("what does a typical exchange feel like?") — better for
  engineers debugging pipeline latency. Long slow calls will drown out short bad
   ones. Right for a performance view.
  - Call-weighted ("what does a typical call feel like?") — better for
  product/support looking at customer experience. A user who had a 2-turn slow
  call had a bad time regardless of how few turns it was. Right for a
  customer-experience view.

  of calls, call-weighted is usually more intuitive — the user expects "these
  100 calls" to be counted as 100 things, not 800 things. But it's your call.

⏺ Choice 3 — "First TTFB per turn" vs "All TTFB samples per turn"

  The backstory

  Each turn in the DB stores TTFB in two forms:

  Form A — single "primary" value (what I'm using):
  turn = {
    llm_ttfb: 0.15,       ← the very first LLM response time in this turn
    stt_ttfb: 0.08,       ← the first STT
    tts_ttfb: 0.22,       ← the first TTS
    ...
  }

  Form B — full sample list (the "_all" arrays):
  turn = {
    llm_ttfb_all: [0.15],           ← 1 LLM call this turn
    stt_ttfb_all: [0.08],           ← 1 STT
    tts_ttfb_all: [0.22, 0.18, 0.19], ← 3 TTS calls (multi-sentence response)
  }

  Why some turns have >1 sample

  A single "turn" can trigger multiple service calls. Most common cases:
  - TTS: The bot's reply gets split into sentences, each spoken separately → 3
  sentences = 3 TTS calls with 3 TTFBs.
  - LLM: If the bot uses a tool (e.g. "check calendar"), the LLM is called once
  for the plan, then again after the tool returns → 2 LLM TTFBs.
  - STT: Rarely >1 — but if VAD flaps mid-utterance, you can get 2.

  Simple example

  One turn where the user asks "Book me a slot Friday at 3pm":
  - STT transcribes it → 1 STT TTFB (say 80 ms)
  - LLM decides to call calendar tool → first LLM TTFB (250 ms)
  - Tool runs, LLM called again with the result → second LLM TTFB (200 ms)
  - Bot's reply "Booked for 3pm Friday" → first TTS TTFB (220 ms)
  - (No second sentence, so no second TTS)

  Form A (current) counts this turn as: llm=250ms, stt=80ms, tts=220ms — 1
  sample per service.
  Form B counts: llm=[250, 200], stt=[80], tts=[220] — 2 LLM samples, 1 STT, 1
  TTS.

  Which is "right"?

  Depends on what the number should describe:

  - Form A (first-only) — "How fast does the bot start responding?" This is what
   the user perceives. The user doesn't care that a tool call added a second
  internal LLM ping; they only feel the wait until the bot starts talking.
  Matches what the per-call detail page shows as the headline TTFB.
  - Form B (all samples) — "How fast is each individual service call?" This is
  what an infra/pipeline engineer cares about — every LLM invocation, every TTS
  sentence. Better for tuning the model provider, catching a slow second
  sentence, etc.

  My take

  Keep Form A (current). Reasons:

  1. Matches the per-call detail page — the headline TTFB numbers you see when
  you click one call are Form A. This page should be consistent with that.
  2. The label on our page is "LLM TTFB" not "LLM call count" — Form A matches
  the user's mental model.
  3. Once we add the histogram chart (next step), Form B would produce
  misleadingly large sample counts on tool-heavy calls, inflating the LLM
  distribution.

  If you ever want a per-call-invocation view, that belongs on a separate
  "pipeline diagnostics" surface, not here.

  Math-wise: p99 rank = 0.99 × 44 = 43.56 → it interpolates between the
  2nd-worst and the worst value.
  With small N, p99 tells you almost nothing about "typical worst 1%". It's just

  3. Per-call averaging hides bad turns inside a good call

  biased.

  5. What's inside end_to_end includes non-pipeline wait

  - STT finalization delay

⏺ What changes if we go turn-weighted instead

  Currently (call-weighted): One sample per call = the call's average turn
  latency.
  Alternative (turn-weighted): One sample per turn — every turn counts equally.

  The main effects, in simple terms

  1. Sample count jumps massively
  - Now: 45 samples (one per call)
  - Then: could be ~500–2,000 samples (one per turn across all those calls)
  - p95/p99 become much more meaningful because you have real statistical power.

  2. Chatty long calls dominate
  - A 30-turn call contributes 30 samples; a 2-turn call contributes 2.
  - If your long calls happen to be well-behaved, the numbers look better than
  reality.
  - If your long calls are the pathological ones, they drag everything down.

  3. Bad individual turns become visible
  - Right now, one 60-second stuck turn buried inside 19 good turns is invisible
   (per-call avg smooths it out).
  - Turn-weighted, that 60s turn is a real sample and lifts the p95/p99.
  - You'd actually see the outliers you can't see today.

  4. The number answers a different question
  - Call-weighted: "What's the typical call experience like?"
  - Turn-weighted: "What's the typical exchange feel like?"

  Simple rule for picking

  - User-experience view → call-weighted (each customer counts once)
  - Pipeline / engineering view → turn-weighted (each measurement counts
  equally, more sensitive to spikes)

  Given your screenshot (Avg 6.62 s vs p95 30 s), you have a bimodal situation —
   most calls fine, a few disasters. Turn-weighted would make the disasters more

  they want. No math changes today.

❯ So will this be a correct approach? ans me in simple                          

⏺ Honest answer: No, it's not statistically correct.

  Why

  "p99 of p99s" is a well-known statistical anti-pattern. Two problems:

  1. It hides the worst turns
  - Say Call A has one 60-second turn buried in 99 good turns.
  - Call A's p99 = 60s (correct, that one turn is the worst).
  - But Call B–J might all have p99 = 2s (no bad turns).
  - Then "p99 across calls" = p99 of [60, 2, 2, 2, 2, 2, 2, 2, 2, 2] →
  basically 60.
  - But you lose the info that 90% of your turns were actually 2s or under —
  because each call collapsed into one number first.

  2. p99 of p99s ≠ real p99
  - A true p99 tells you: "1% of all measurements were worse than this."
  - p99 of p99s tells you: "the worst-1%-per-call's worst-per-call value."
  - These are not the same number, and the second one is meaningless — no user
  in the real world experiences "the p99 of a call". They experience individual
  turns.

  3. Very small numbers hide statistical noise
  - With only 10 calls, "p99 across 10 numbers" = basically the max of those 10
  numbers. It's not a percentile in any meaningful sense.

  What's actually correct

  Compute p50/p95/p99 directly on all raw turn samples — which is exactly what
  we're doing now. This is what Datadog / Grafana / every real APM tool does.

  When 2-step aggregation is used

  Only in one case: when you can't afford to store all raw samples (e.g., you're
   aggregating billions of events across a cluster). Then you approximate. Even
  then, you use "t-digests" or "HDR histograms" — not naive p99-of-p99.

  You have all the raw turn data. There's no reason to approximate.

  My recommendation: keep what we have. If you want to slice differently (e.g.,
  "which calls have the worst p99?"), that's a different question and belongs on
   a table view, not the aggregate.

  Want me to explain what to look for instead if you're trying to spot bad
  calls?

⏺ Current flow — in simple English

  Step 1 — Get all the calls in your filter scope
  The backend runs the same query the table uses (date range + filters) and
  returns matching calls with their turn_metrics.

  Step 2 — Flatten every turn into one big list
  For each call:
  - Look at its turn_metrics array
  - Take each turn's end_to_end value (and separately llm_ttfb, stt_ttfb,
  tts_ttfb)
  - Throw away nulls and zeros (bad/missing measurements)
  - Put every remaining number into one pool

  Example (2 calls):
  - Call A turns: [1.2s, 2.1s, null, 0.9s] → 3 values → pool: [1.2, 2.1, 0.9]
  - Call B turns: [3.0s, null, 4.5s] → 2 values → pool: [1.2, 2.1, 0.9, 3.0,
  4.5]

  Final pool for end-to-end: 5 samples.

  Step 3 — Compute stats on the pool
  From that single pool of numbers:
  - Avg = mean
  - p50 = the middle number (half are below, half above)
  - p95 = value below which 95% of numbers fall
  - p99 = value below which 99% of numbers fall
  - Min / Max = smallest and largest
  - Histogram = count how many fall into each bucket (<1s, 1–2s, 2–3s, …)

  Step 4 — Repeat for each metric
  Same 4 steps for LLM TTFB, STT TTFB, TTS TTFB, end-to-end latency.

  That's it

  Each metric = 1 pool of turn measurements → compute stats on that pool
  directly. No per-call intermediate step, no 2-stage aggregation. Just raw data
   → percentiles.

  This is the standard latency-dashboard math (Datadog, Grafana, Prometheus all
  do exactly this).
